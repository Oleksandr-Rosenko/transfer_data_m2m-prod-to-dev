# Перенос повідомлень Prod → Dev (M2M)

Streamlit-застосунок: беремо повідомлення об'єкта з Prod (`my.m2m.eu`) і «програємо» їх на dev-сервер так,
ніби їх надсилає трекер. Потрібен розробникам, щоб тестувати на реальних даних.

## Як користуватись

1. Бічна панель: увійдіть на Prod (логін і пароль живуть лише в сесії браузера й ніде не зберігаються).
2. **Об'єкт-джерело**: пошук за назвою або IMEI.
3. **Куди переносимо**: протокол, адреса й порт dev-сервера, IMEI об'єкта на dev (його треба створити заздалегідь).
   Кнопка «Перевірити з'єднання з dev» робить лише handshake, дані не надсилає.
4. **Період** (київський час) і режим часових міток:
   - *зсунути* — кінець періоду стає «зараз мінус N хв», інтервали між точками зберігаються;
   - *залишити оригінальні дати*.
5. **Попередній перегляд**: кількість повідомлень, перше й останнє, графік напруги.
6. «Пробний запуск» надсилає лише перші 20 повідомлень, щоб перевірити, що dev їх приймає.
7. «Почати перенос»: прогрес у відсотках, лічильник повідомлень, швидкість, залишок часу, журнал помилок,
   «Зупинити» та «Повторити невдалі».

> Якщо перенести той самий період двічі, на dev можуть з'явитись дублікати.

**Порядок точок.** Перед відправкою точки за замовчуванням впорядковуються за UTC-часом (галочка «Впорядкувати
точки за UTC-часом перед відправкою»). Це потрібно, бо Prod може віддати їх не за хронологією, і dev, який рахує
пробіг (`totalDistance`, `m2m_odo`) за порядком надходження, отримає «стрибки» на десятки кілометрів.
Впорядкування працює з буфером у 2 години, тож пам'ять не росте разом з періодом.

## Діагностика порядку точок

У вкладці «Виправлення порядку точок» крок «Перевірити порядок» лише читає дані. Він проходить усі точки об'єкта за період у порядку, в якому їх віддає API, і показує, де UTC-час
«йде назад». Типовий випадок — ніч переходу на зимовий час (остання неділя жовтня): година 03:00–03:59 за Києвом
повторюється, і якщо платформа сортує за локальним часом, точки двох годин перемішуються, а трек на мапі
«зигзагом» стрибає між двома місцями. Для кожного фрагмента видно діапазон, максимальний відкат часу, кількість
стрибків координат та імовірну причину. Також рахуються точки з координатами 0,0 (невалідний GPS-фікс) та інші
стрибки координат. Кнопка «Завантажити CSV» віддає проблемні відрізки в правильному порядку (з колонкою `№ у API`),
щоб передати розробникам платформи.

Те саме з командного рядка:

```bash
M2M_PASSWORD='...' python scripts/check_order.py --email me@company.eu --device-id 7994 \
    --from "2026-10-25 02:00" --to "2026-10-25 06:00" --csv order_7994.csv
```

Код виходу: 0 — порядок правильний, 1 — знайдено порушення, 2 — помилка.

## Вкладка «Виправлення порядку точок»

Окремий інструмент для **одного середовища** (з власним входом, незалежним від вкладок переносу й діагностики):
вхід у потрібну систему → пошук об'єкта й період → «Перевірити порядок» (завантажує точки й показує інтервали,
де час іде назад) → налаштування сервера приймання цього середовища (протокол, адреса, порт; IMEI/ID береться
з самого об'єкта) → «Підготувати» (показує інтервал і кількість; нічого не змінює) → підтвердження введенням
домену → «Виправити порядок».

Що робить: читає точки інтервалу, зберігає резервну копію (`.json.gz`), видаляє їх (лише цей об'єкт і лише
цей інтервал), відправляє ті самі повідомлення назад із виправленим часом у хронологічному порядку й перевіряє результат.

**Причина проблеми (за даними реального об'єкта).** У ніч переходу на зимовий час друга година 03:xx зберігається
платформою з міткою першої: `deviceTime`, `fixTime` і `serverTime` збігаються, а годинник трекера (`sns16486`, UTC)
показує справжній момент, на 1 год пізніший. Через це точки двох годин мають однакові мітки й перемішуються,
а сортування нічого не виправляє. Скрипт визначає такі точки за різницею `sns16486 − мітка ≈ +1 год` (у годині
переходу, допуск 10 хв), записує їх із міткою +1 год і лише тоді впорядковує. Для об'єктів без параметра
`sns16486` виправити час неможливо: у цьому разі діагностика лише попереджає про стрибки координат.

Гарантії:

- **Лише цей об'єкт і лише цей інтервал.** Видаляються тільки id, щойно прочитані для вибраного об'єкта в
  інтервалі (проблемні фрагменти ±2 год, або до кінця періоду). Інші об'єкти й точки поза інтервалом не чіпаються.
- **Перевірки до першої зміни** (якщо не пройшла будь-яка, нічого не змінюється): `uniqueId` об'єкта збігається
  з IMEI/ID відправки; сервер приймання відповідає; кількість не змінилась після «Підготувати»; API повернуло
  лише точки інтервалу.
- **Перевірка після змін:** кількість повідомлень та сама, порядок читання правильний (за бажанням ще й збіг
  пробігу з довжиною треку).
- **Автовідкат:** помилка, відхилена точка, розбіжність кількості, порядок, що не виправився, або «Зупинити» →
  інтервал очищується й відновлюється з резервної копії в початковому порядку. Якщо відновлення не вдалось,
  застосунок каже про це прямо й залишає резервну копію.

Обмеження:

- Якщо прийом (ingest) знову збереже точки другої години з міткою на 1 год раніше, перевірка після змін це
  побачить (час у них знову розійдеться з годинником трекера), і інтервал буде повернуто як був. Тоді виправлення
  можливе лише в бекенді (збереження часу в годині переходу).
- Вкладка «Перенос Prod → Dev» копіює мітки часу Prod як є, тож у копії ця помилка відтворюється.
- Відновлені повідомлення мають нові внутрішні id; похідні поля (`totalDistance`, пробіг) платформа рахує за порядком
  надходження. Параметри без відповідності в `m2m_replay/mapping.py` у відправку не потрапляють (і при відновленні
  теж): список показується після завершення, а самі значення лишаються в резервній копії.
- Спершу пробуйте на dev. Для іншого середовища підтвердження вимагає ввести його домен.

## Протоколи

| Протокол | Порт за замовчуванням | Що передається |
|---|---|---|
| Teltonika Codec 8E (рекомендовано) | 5027 | усі сирі IO трекера, ID до 65535 |
| Teltonika Codec 8 | 5027 | те саме, але лише IO з ID ≤ 255 (решта пропускається й показується у звіті) |
| Wialon IPS 2.0 / 1.1 | 5039 | усі параметри точки як є; службові — за галочкою |

Одне TCP-з'єднання на весь перенос; повідомлення йдуть пакетами (за замовчуванням по 100, максимум 255).
Якщо сервер підтвердив лише частину пакета, повторно надсилається тільки решта. Обрив з'єднання — до 3 спроб
з перепідключенням. Якщо перші 3 пакети відхилено повністю, перенос зупиняється з поясненням.

### Які параметри переносяться

У точці на платформі є дві групи параметрів:

- **дані трекера**: `io_<ID>` та іменовані (`power`, `battery`, `ignition`, `rssi`, `odometer`, `operator`,
  `hdop`, `pdop`, ...), які платформа вже перетворила з IO. Для Teltonika вони повертаються в IO за таблицею
  `NAMED_TO_IO` у `m2m_replay/mapping.py` (наприклад, `power` 12.084 В → IO 66 = 12084 мВ);
- **службові параметри платформи**: `pf_*`, `power_enb`, `power_filtered`, `m2m_*`, `distance`, `totalDistance`,
  `_MOTION`. Через Teltonika їх передати неможливо, dev порахує їх сам із вхідних даних.
  У Wialon IPS їх можна передати за галочкою «Передавати й службові параметри».

Координати беруться «сирі», від трекера (`pf_orig_lat/lon`), а якщо їх немає — з точки.
Таблиця `NAMED_TO_IO` складена за документацією Teltonika (серія FMC/FMB) і звірена з вашими CSV-вивантаженнями
(усі ключі розпізнаються, 22 IO). Якщо на dev якийсь параметр з'являється під іншою назвою, виправте ID там.

## Запуск локально

```bash
pip install -r requirements.txt
cp .streamlit/secrets.toml.example .streamlit/secrets.toml   # за потреби
streamlit run app.py
```

## Streamlit Community Cloud

1. New app → цей репозиторій, гілка `main`, **Main file path: `app.py`**.
2. App → Settings → **Secrets**: вміст `.streamlit/secrets.toml.example` (адреса й порти dev).
3. Після кожного пушу в `main` застосунок перезбирається сам.

⚠️ Хмара Streamlit ходить на dev з публічних адрес. Якщо порт 5027/5039 відкритий лише для певних IP,
кнопка «Перевірити з'єднання з dev» покаже помилку підключення: тоді відкрийте порт або запускайте застосунок
на машині всередині мережі.

## Структура

```
app.py                  інтерфейс: вкладка «Перенос» (налаштування і прогрес) та «Виправлення порядку точок» (перевірка й виправлення)
m2m_replay/
  client.py             API платформи: вхід, пошук об'єктів, точки за період (паралельне завантаження сторінок)
  models.py             Point, розбір часу й атрибутів
  mapping.py            відповідність параметрів платформи ↔ IO / параметри Wialon
  teltonika.py          кодування Codec 8/8E, відправник
  wialon.py             кодування IPS 1.1/2.0, відправник
  replay.py             фонове завдання, зсув часу, пакети, повторні спроби, попередній перегляд
  order.py              порядок точок: впорядкування за UTC для переносу, діагностика, експорт
  fix.py                виправлення порядку на dev: перевірки, резервна копія, видалення, відправка, відкат
scripts/
  check_order.py        діагностика порядку точок з командного рядка
tests/                  модульні й наскрізні тести (мок-сервери Teltonika і Wialon)
```

## Тести

```bash
python -m unittest discover -s tests -v     # або: pytest
```

Що перевірено: CRC і байти пакета Codec 8 збігаються з офіційним прикладом Teltonika; незалежний декодер
розбирає Codec 8 і 8E; повний перенос через мок-сервери (час, порядок, ID > 255, часткові ACK, обрив і перепідключення,
відмова сервера, невідомий IMEI, зупинка, повторення невдалих); мапінг усіх ключів із реальних CSV.

Що **не** перевірено автоматично: прийом на справжньому dev-сервері (особливо Wialon IPS: специфікацію реалізовано,
але проти реального сервера не запускали) та сам інтерфейс у справжньому Streamlit. Тому перший раз використайте
«Пробний запуск» і подивіться результат на dev.
